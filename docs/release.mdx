# Release Automation

This repo uses Release Please for independent Dart package releases.

Release configuration lives in:

- `release-please-config.json`
- `.release-please-manifest.json`
- `.github/workflows/agent-auto-approve.yml`

Release tags use `<package>-v<version>`:

- `ecsly-v0.1.0-dev.x`
- `ecsly_app-v0.1.0-dev.x`
- `ecsly_codegen-v0.1.0-dev.x`
- `ecsly_flutter-v0.1.0-dev.x`
- `ecsly_serialization-v0.1.0-dev.x`
- `ecsly_replay-v0.1.0-dev.x`

The tag workflow validates the package/version pair before publishing. Local
maintainer preflight:

```sh
dart tool/release/pub_package.dart --all --skip-existing
dart tool/release/pub_package.dart --tag ecsly-v0.1.0-dev.13 --skip-existing
just publish-tag-dry-run ecsly_flutter-v0.1.0-dev.5
```

Automated tag publishing requires two hosted settings:

1. `RELEASE_PLEASE_TOKEN` must be configured as a write-capable repository
   secret. Release Please must not fall back to `GITHUB_TOKEN`, because tags
   created with the default token may not start the downstream publish workflow.
2. Each package must enable pub.dev GitHub Actions publishing for repository
   `Arenukvern/ecsly`, tag pattern `<package>-v{{version}}`, push events, and
   the required GitHub Actions environment `pub.dev`.

Verify the release token before relying on automatic tags:

```sh
gh secret list --repo Arenukvern/ecsly
```

Maintainers can bootstrap or rotate the secret from an authenticated GitHub CLI
session that has `repo` and `workflow` scopes:

```sh
gh auth status
gh auth token | gh secret set RELEASE_PLEASE_TOKEN --repo Arenukvern/ecsly
```

Do not print the token in logs. The secret value lives only in GitHub Actions;
the repo records the required secret name, scopes, and verification command.

Bootstrap matters: pub.dev automated publishing only works after the first
version of a package exists. All six current packages are published and have
GitHub Actions publishing configured (`ecsly_serialization` and
`ecsly_replay` were bootstrapped manually on 2026-11-07). For any FUTURE
package, bootstrap once from its release tag, then enable automated
publishing on its pub.dev admin page:

```sh
git fetch --tags && git checkout <package>-v<version>
dart pub get
cd <package-dir> && dart pub publish --force   # flutter pub publish for Flutter packages
```

Recovery: a tag publish that failed in CI can be re-driven without re-tagging:

```sh
gh workflow run pub-publish.yml --ref <package>-v<version> \
  -f tag=<package>-v<version> -f execute=true
```

Dispatch the workflow **at the tag ref** (`--ref <tag>`): pub.dev requires the
OIDC token's `ref_type` to be `tag` even for `workflow_dispatch` runs, and a
dispatch against `main` carries `ref_type: branch`, which pub.dev rejects. The
tag ref also guarantees the checked-out pubspec versions match the tag, which
the preflight enforces. pub.dev must allow `workflow_dispatch` publishing for
that package — it is enabled for all six.

The release helper keeps the same package order for automation, uses
`flutter pub publish` for `ecsly_flutter`, checks package changelog entries, and
waits for internal hosted dependencies before publishing dependent packages.

Release Please is still the source of truth for release PR versions through
`.release-please-manifest.json`. Because the Dart updater can format prerelease
pubspec versions incorrectly, release PRs run
`.github/workflows/release-pr-sync-pubspecs.yml`, which normalizes every
package `pubspec.yaml` (core and plugins) from the manifest and syncs
`docs.json`'s version variable with the core pubspec. Maintainers can run the
same sync locally:

```sh
just sync-release-pubspecs
just check-release-pubspecs
just sync-benchmarks
```

Agent auto-approval is label-gated. Configure `AUTO_APPROVE_TOKEN` with a
separate write-capable machine user token. Release Please PRs from
`github-actions[bot]` are labeled automatically; trusted same-repo `codex/` PRs
still need an explicit `agent-auto-approve` label.
